# `developer.homebrew.cache` rule review

Status: bundled revision 1, discovery-only, unschedulable, and non-executable.

Reviewed: 2026-07-29 against Homebrew's official command documentation. This
is an independent DUX review. It does not derive policy, code, fixtures, or
wording from Mole or another cleanup product.

## Vendor evidence

The Homebrew manual documents `brew --cache` as the command that displays
Homebrew's download cache and documents two relevant cleanup forms:

- [`brew cleanup`](https://docs.brew.sh/Manpage#cleanup-options-formulacask-)
  removes stale lock files and outdated downloads, and removes old installed
  formula versions unless the caller chooses otherwise.
- [`brew cleanup --prune=all`](https://docs.brew.sh/Manpage#cleanup-options-formulacask-)
  removes all cache files, while
  [`rm -rf "$(brew --cache)"`](https://docs.brew.sh/Manpage#cache-options)
  is documented as deleting all cached downloads, including downloads for
  currently installed formulae.

These sources establish that Homebrew's download cache can be regenerated by
downloading artifacts again. They do not establish that deleting it is free:
future installs, upgrades, or repairs may require network access, time, and
bandwidth. DUX therefore says “regenerable,” not “unneeded.”

## Revision 1 discovery evidence

The immutable targeted-scan evaluator requires all of the following:

1. the engine selected its code-owned `UserCacheDirectory` evaluator scope for
   the exact known-cache targeted scan;
2. an exact, case-sensitive direct child directory named `Homebrew` exists
   immediately below the scanned current-account `Library/Caches` root;
3. the candidate itself is not a symlink;
4. the candidate and every recorded regular file or directory below it have a
   representable modification time; and
5. the newest such observation is at least seven inclusive days old at the
   evaluator's exact persisted instant.

Nested directories named `Homebrew`, a differently cased component, a regular
file with that name, and a selected/configured-root scan do not match this
rule. The candidate's `estimated_bytes` is the historical scan aggregate. It
is an observed estimate, not a verified reclaim amount.

Coverage is candidate-local. An issue at the cache root, an ancestor, or inside
`Homebrew` blocks the age fact; an unrelated issue below a sibling such as
DUX's deliberately excluded cache does not taint this candidate. Unknown
coverage always blocks it. Any symlink observed in the candidate subtree adds
`SymlinkBoundary`.

The seven-day fact is recency evidence only. DUX does not currently observe
Homebrew processes, locks, downloads in progress, package ownership, or the
live cache location returned by `brew --cache`. The candidate therefore always
retains both `MissingOrIncompleteEvidence` and `ProtectedPath`, even when its
age and coverage are complete.

## Policy and authority boundary

The catalog carries `SafeRegenerable` and
`RemoveKnownRegenerableContents` as proposed presentation policy. Revision 1
is not selectable while blocked, is not schedule eligible, cannot construct a
cleanup plan, has no provider command or filesystem executor, and crosses no
FFI cleanup boundary. AI may later explain this finding but cannot remove its
blockers or authorize an action.

A future promotion would need a separately reviewed provider-aware live
witness for the current cache location and active Homebrew work, exact
descendant policy, no-follow identity and hard-link checks, protected-root and
volume proof, changed-since-scan revalidation, and an explicit reviewed plan.
This discovery rule supplies none of that authority.

## Adversarial coverage

Core evaluator and immutable-snapshot replay tests cover exact direct matching,
wrong case/kind/location, selected-scope isolation, inclusive age, missing and
recent timestamps, candidate-local partial coverage, unrelated sibling
exclusions, descendant symlinks, exact scope/scan-ID binding, durable replay,
and stale evaluator replacement. Positive candidates remain unschedulable and
blocked by `MissingOrIncompleteEvidence` plus `ProtectedPath`.
