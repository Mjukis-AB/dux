# `developer.python.pycache` rule review

Status: bundled revision 2, discovery-only, unschedulable, and non-executable.

Reviewed: 2026-07-18 against the Python import-system documentation and PEP
3147. This is an independent DUX review. It does not derive policy, code,
fixtures, or wording from Mole or another cleanup product.

## Vendor evidence

Python's import system stores generated bytecode in a `__pycache__` directory
next to the source module. The Python programming FAQ documents that importing
a module creates a `.pyc` file in that directory when Python can write it. The
import system validates timestamp- and hash-based bytecode against the source,
and regenerates a cache when the cached representation is missing or stale:

- [Python import-system reference: cached bytecode invalidation](https://docs.python.org/3/reference/import.html#cached-bytecode-invalidation)
- [Python FAQ: creating a `.pyc` file](https://docs.python.org/3/faq/programming.html#how-do-i-create-a-pyc-file)
- [PEP 3147: `__pycache__` repositories](https://peps.python.org/pep-3147/)

These sources establish that ordinary import bytecode is reproducible from the
source module. Rebuilding still consumes CPU and can be delayed by the active
interpreter, so “regenerable” does not mean that deletion is without a user
visible cost.

## Revision 2 discovery evidence

The immutable scan classifier requires all of the following:

1. an exact directory component named `__pycache__`;
2. a direct regular, non-symlink sibling whose filename has the exact,
   case-sensitive `.py` extension; and
3. no followed or unfollowed symlink component in the candidate ancestry.

The sibling source is supporting snapshot evidence that this cache directory
belongs to a Python source tree. It does not prove that every descendant was
written by Python, that the interpreter will use this directory, or that the
source is still present at action time. Python can relocate caches with
`PYTHONPYCACHEPREFIX`/`sys.pycache_prefix`, and DUX intentionally does not infer
those external locations from this rule.

The rule carries `SafeRegenerable` and
`RemoveKnownRegenerableContents` as proposed policy, but every production
candidate still has `ProtectedPath`. It is not selectable, cannot construct a
cleanup plan, is not schedule eligible, crosses no FFI cleanup boundary, and
cannot reach a filesystem effect.

## Explicit exclusions and future authority requirements

This rule does not match arbitrary `.pyc` files outside `__pycache__`, virtual
environments (`venv`/`.venv`), `.tox`, package-manager directories, source
files, or user-selected directories merely named `__pycache__` without a
direct `.py` sibling. A future authority witness must independently reject
symlinks, special entries, hard-linked files, non-`.pyc` descendants, changed
source/marker identity, active Python writers, protected roots, and incomplete
scan coverage before any permanent removal is considered. None of those
witnesses exists in this discovery slice.

## Adversarial coverage

Core projection/evaluator and snapshot-replay tests cover the positive direct
`.py` marker, missing marker, wrong-case extension, marker symlink, candidate or
ancestor symlink, nested-artifact suppression, deterministic evidence
selection, and exact replay. The safe policy remains unschedulable and the
candidate retains its `ProtectedPath` blocker in every positive case.
