# DUX - Development Notes

## Release Checklist

Before creating a release tag:

1. **Bump version** in `Cargo.toml` (workspace version) and update `dux-cli/Cargo.toml` dependency on `dux-core` to match
2. **Run checks locally**:
   ```bash
   python3 -m unittest discover -s scripts/tests -p 'test_*.py'
   python3 scripts/check_destructive_calls.py
   cargo fmt --all -- --check
   cargo clippy --workspace --all-targets --locked -- -D warnings
   RUSTFLAGS='--cfg fuzzing' cargo clippy --package dux-core --all-targets --locked -- -D warnings
   CLIPPY_CONF_DIR="$PWD/fuzz" RUSTFLAGS='--cfg fuzzing' cargo clippy --manifest-path fuzz/Cargo.toml --all-targets --locked -- -D warnings
   cargo test --workspace --all-targets --locked
   cargo +1.88.0 check --workspace --all-targets --locked
   RUSTFLAGS='--cfg fuzzing' cargo +1.88.0 check --package dux-core --all-targets --locked
   cargo audit --deny warnings
   cargo audit --file fuzz/Cargo.lock --deny warnings
   cargo deny --locked check
   cargo deny --manifest-path fuzz/Cargo.toml --locked check --config fuzz/deny.toml
   cargo package --workspace --locked
   bash -n dux-macos/scripts/*.sh scripts/*.sh
   bash scripts/check_macos_deployment_target.sh <each macOS release Mach-O>
   ```
3. **Consider cross-platform issues**: Code inside `#[cfg(target_os = "macos")]` won't be compiled on Linux CI - ensure no unused variables leak out
4. **Commit and tag**: `git tag vX.Y.Z && git push origin main --tags`

The tag workflow is strictly ordered: validation/security, four-target builds, crates.io, draft GitHub release plus `SHA256SUMS`, then Homebrew. All actions must remain pinned to full commit SHAs. `HOMEBREW_TAP_TOKEN` must be a fine-grained PAT scoped only to `mjukis-ab/homebrew-tap` with Contents read/write; it is passed only to inline Git in the final job.

## Architecture

- **dux-core**: Core library with tree data structures, scanner, and cache
- **dux-cli**: TUI application using ratatui
- **dux-ffi**: Minimal UniFFI boundary; keep exports coarse, owned, versioned, and free of presentation or cleanup policy
- `dux-core::projection` owns `ArtifactKind`, evidence-gated artifact classification, large-file projection, and clock-injected staleness evaluation. Marker IDs and paths are snapshot evidence, never cleanup authorization; mutation callers must revalidate them. Keep CLI dirty-state coordination, threshold cycling, and display labels out of core.
- `dux-core::domain` owns product-neutral rule/candidate policy. A `RuleRef` always carries stable ID plus nonzero revision; validated rules own category/safety/action/schedule policy, candidates copy those fields, and typed evidence/blockers remain scan facts only. Production candidate construction is crate-private and accepts only the completed fresh-scan witness plus the engine-selected scope. The catalog mixes selected-root and exact user-cache-directory observations: nine rules remain Informational/RevealOnly, while the reviewed Rust target, Python bytecode, Homebrew download, and pip cache rules may propose SafeRegenerable/RemoveKnownRegenerableContents but remain unschedulable and blocked by unresolved authority. The two cache-root rules additionally always retain `MissingOrIncompleteEvidence`; age is not provider-inactivity proof. Never interpret a persisted candidate, `has_cleanup_operation`, `has_no_known_blockers`, or a rule scheduling flag as planner/executor authority. Keep localized copy in clients via stable text keys and keep schema DTOs, path validation, plans, persistence, FFI DTOs, AI, and execution in their dedicated layers.
- `dux-core::persistence` owns checksummed SQLite schema versions and non-authoritative history. Schema v2 preserves migrated v1 candidate/cleanup rows only as incomplete legacy summaries and stores new ordered paths/evidence/blockers, frozen cleanup effects, and recovery generations separately. Schema v4 binds one strict evaluation lifecycle to the exact succeeded scan snapshot, evaluator/catalog/context identity, normalized time, and complete candidate batch or typed failure; normal engine publication commits that graph in one transaction, while historical scans receive no fabricated rows. Schema v13 stores only a domain-separated digest of the code-owned admitted scan-root filesystem identity and an exact-root/time lookup; legacy `NULL` identities never satisfy cross-scan comparability, and the digest is observation data rather than a filesystem witness or cleanup capability. The typed candidate/evaluation readers return distinct observation records rather than domain authority, validate bounded children, status/count/time/snapshot/policy/evidence invariants, and reject legacy pollution or post-evaluation standalone inserts. The typed cleanup boundary records complete `planned` observations after exact candidate-fact matching; its separate sealed journal lease retains the cleanup lock, is non-shareable, internally generates an owner, and exact-CASes typed owner/generation transitions. Full bounded journal loads validate the frozen plan plus every dynamic child, derived result, generation, timestamp, and effect-provenance shape. Same-scope recovery writes only for `DefinitelyGone`; `Alive`, `Unknown`, changed boot scope, and Windows death are not recovery authority. Durable effect-start receipts are ordering evidence only, reject cancellation at final revalidation, and this layer performs no effect. Never deserialize a stored candidate/plan into cleanup authority, infer interruption or an effect result from process death, expose raw SQL/owners through FFI/CLI/AI, or let heartbeat age authorize recovery.
- Cleanup-plan records are immutable review data, not approval or executor witnesses. They freeze candidate/rule/scan facts for 15 minutes, derive mandatory estimate/mode warnings, and distinguish Trash, permanent removal, and cloud eviction. Their constructor remains private inside `dux-core::domain::cleanup_plan` until canonical path validation can supply planner-owned target witnesses. Do not expose plan construction to FFI, CLI, Swift, AI, or arbitrary paths; do not add `can_execute`, approval, mode-mutation, or filesystem behavior to these domain records.

Windows inspection currently reopens cumulative full paths rather than resolving relative to retained handles, so it must not become actionable until the executor has handle-bound or equivalent revalidation. Never accept cache-rebuilt `DiskTree` paths as cleanup identity: cached names are currently reconstructed from lossy strings, and the later planner must enforce fresh/lossless scan provenance with a typed source witness before calling this bare-path validator. Keep validator construction out of FFI, clients, AI, and cleanup plans except through their explicit reviewed authority slices.

Cached/public trees and non-completed traversal outcomes cannot mint that witness. Durable engine scan tasks are the only current producer. Cancelled/failed work receives no snapshot reference, but a completed traversal can leave an unreferenced immutable orphan if publication succeeds before an unreconciled SQLite completion failure. The store uses marker-complete private provisioning, unique temps, atomic no-replace publication, exact 0700/0600 or protected-DACL validation, read-only retained final handles, and full winner decode. Snapshot mutation order is SQLite connection → SQLite writer/compatibility lease → snapshot writer; publication retains the snapshot lock through the exact scan-summary CAS and post-commit revalidation. Every load first checks the schema-v5 exact-identity tombstone under a current-schema database guard, including already-guarded reconciliation paths; a tombstone wins before file open and never rewrites the terminal reference. Schema-v6 review acquisition uses the same lock order and retains a validated file handle after pin commit; renewal/release are exact and Drop never enters persistence. The schema-v7 inventory sequentially opens, captures, and closes each physical entry, measures logical and platform allocation bytes, then sequentially reopens names and requires final/control usage to remain exact. Schema v8 commits an immutable row before creating each production temp and retains an exclusive kernel lock for the staging lifetime. Inventory classifies row-bound active/quiescent and unleased temps. An exact same-scan retry may remove only its own identity-revalidated quiescent residual. The separate sealed terminal-temp batch may consume at most one exact row whose fully decoded parent is failed, cancelled, or interrupted with no snapshot: it skips active rows, never touches running or unleased debt, revalidates name/identity/usage and the kernel lock, freezes checked accounting, removes physical bytes before the row, closes the delete handle before directory sync, and preserves post-unlink or post-row-delete uncertainty as `OutcomeUnknown`. Only typed idle-only `SnapshotTerminalTempMaintenance` can invoke it, with no authority-bearing input, one call, path-free aggregates, Applying cancellation linearization, and no self-enqueue. The separate physical-only unleased-temp batch holds the same database-before-snapshot locks, subtracts the complete at-most-64-row lease-name population from one bounded marker-owned inventory, and may remove only the first lexicographic quiescent exact-generated-grammar temp after fresh no-follow identity/usage/private/name/one-link and second kernel-lock proof. It checks accounting before effect, closes the delete handle before directory sync, maps post-unlink uncertainty to `OutcomeUnknown`, mutates no SQLite row, and never adopts or maps the file to a scan. Only typed idle-only `SnapshotUnleasedTempMaintenance` may invoke it with one call, path-free aggregates, Applying cancellation linearization, and no self-enqueue. Prefix/PID/age/mtime/quiescence alone never grant authority. For pre-v8 version skew, Windows old writable handles deny delete sharing; Unix can detach an old writer's non-v8-locked inode, after which its current-schema/name publication proof fails. This residual same-user availability race is outside the 0700/0600 or protected-owner-DACL private-store boundary and requires not concurrently running incompatible binaries. Successful publication consumes the row atomically with scan completion; Drop is close-only. Inventory itself never full-decodes bodies or grants final-retention mutation authority. The sealed one-final cap batch repeats all policy under the database-before-snapshot locks, fully decodes the exact candidate, commits the append-only tombstone first, then removes only the retained identity and syncs the directory; tombstoned residual retry repeats full-content validation. The separate sealed one-final physical-orphan batch proves a typed final has zero exact catalog references under the same lock order, fully decodes the body, binds the filename to its scan ID, and requires an exact guarded parent/root/status with no snapshot reference. It creates no tombstone and mutates no scan, temp, pin, or history row; checked accounting precedes identity/usage-revalidated removal, and post-unlink uncertainty is `OutcomeUnknown`. Only the typed idle-only `SnapshotOrphanMaintenance` task may call it, with no authority-bearing input, one repository call, path-free aggregate output, Applying cancellation linearization, and no self-enqueue. Never provision or mutate after a newer database schema wins, replace a deterministic collision, let retention invert this lock order, infer an open review from candidate/session state, treat PID/age/quiescence as deletion authority, or treat a checksum/path/device/inode alone as cleanup authority. Broad/unproven and legacy provisioning-stage handling, cross-reboot running-row policy, native Windows mutation runtime verification, paged FFI/Swift/CLI snapshot transport, and the legacy cache remain separate work; exact-marker-owned root-local reconciliation uses the sealed boundary below; coverage belongs to the SQLite scan summary rather than the snapshot wire.

## Cache System

- Cache stored in `~/.cache/dux/` (or platform equivalent via `dirs` crate)
- Format: Magic + Version + Metadata + Tree (postcard) + CRC32
- `TreeNode.path` and `is_expanded` are `#[serde(skip)]` - reconstructed on load via `rebuild_paths()`
- `TreeNode.mtime` is captured for files and directories from the same metadata used for size, serialized since cache v6, and remains snapshot evidence rather than mutation authority. Cache v7 invalidates older per-path hard-link totals after deterministic physical-allocation deduplication. Followed links retain `path_is_symlink` while using target metadata; pre-Unix-epoch values unsupported by Serde remain `None`.
- Bump `CACHE_VERSION` in `dux-core/src/cache/metadata.rs` when format changes
- Cache age always means the tree's original scan time; deletion-only cache updates must preserve it.
- `r` starts a cache-bypassing rescan. Keep the previous tree and dirty state until the replacement scan succeeds so failure or quit cannot lose the last usable snapshot.
- Writers use exclusively created `.<cache>.<pid>.<counter>.tmp` files and atomic rename. Join older in-process writers before publishing a newer snapshot; cross-process writes are still last-writer-wins.

## Tree Structure

- Arena-allocated with `Vec<Option<TreeNode>>` - `None` = tombstone (deleted)
- `remove_node()` tombstones node + descendants and propagates size changes up to root
- Footer selection bytes and multi-delete planning use the same effective selection: selected descendants are omitted when an ancestor is selected. The displayed selection count remains the raw number of highlighted rows.

## Deletion

- The CLI is read-only. Its former `d` action, confirmations, background
  workers, raw recursive-delete adapter, and destructive-call exceptions are
  retired. Preserve scanning, navigation, selection, computed views, history,
  and reveal.
- Any future CLI cleanup must consume the same current, unexpired,
  reviewed-plan executor as the native product. It must not accept a caller
  path, reconstruct authority from the legacy cache, or own filesystem-effect
  workers.
- Explorer Trash and the private permanent-safe Rust-target driver are separate
  reviewed effect boundaries. Permanent-safe native execution remains
  Debug-only until every `SECURITY_DESIGN.md` §17.3 gate is satisfied.
- Cached tree names and marker classifications are observations only. Never
  convert them directly into cleanup identity or report scanned bytes as
  verified freed capacity.

## Build Artifact Classification

- Classification is fail-closed and tree-aware; directory names alone are not evidence.
- Markers must be exact-case, direct sibling/child regular files and must not be symlinks.
- Current rules: Cargo `target` + sibling `Cargo.toml`; Node `node_modules` + sibling `package.json`; Gradle `build`/`.gradle` + a sibling Gradle build/settings script; Python `__pycache__` + sibling `.py`, `.tox` + sibling `tox.ini`, and `.venv`/`venv` + child `pyvenv.cfg`; CocoaPods `Pods` + sibling `Podfile` + child `Manifest.lock`; Next/Nuxt output + sibling `package.json` + matching framework config.
- `DerivedData`, `Build`, `dist`, `vendor`, and `.cache` are intentionally not classified yet.
- “Marker-matched” means likely tooling ownership, not guaranteed reproducibility. It grants no cleanup authority.
- `developer.rust.target` revision 3 additionally requires complete file/directory
  mtime coverage and an inclusive seven-day age at the evaluator's exact
  scheduled instant. Preserve the same cutoff semantics in snapshot replay,
  plan preview, pre-effect admission, and the descriptor-relative driver.
  Historical sealed revision-2 sessions may be decoded only for recovery
  terminalization; never let that compatibility mint or restore effect
  authority.
