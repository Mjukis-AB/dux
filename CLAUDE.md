# DUX - Development Notes

## Release Checklist

Before creating a release tag:

1. **Bump version** in `Cargo.toml` (workspace version) and update `dux-cli/Cargo.toml` dependency on `dux-core` to match
2. **Run checks locally**:
   ```bash
   python3 -m unittest discover -s scripts/tests -p 'test_*.py'
   python3 scripts/check_destructive_calls.py
   cargo fmt --all -- --check
   cargo clippy --workspace --all-targets --locked -- -D warnings
   RUSTFLAGS='--cfg fuzzing' cargo clippy --package dux-core --all-targets --locked -- -D warnings
   CLIPPY_CONF_DIR="$PWD/fuzz" RUSTFLAGS='--cfg fuzzing' cargo clippy --manifest-path fuzz/Cargo.toml --all-targets --locked -- -D warnings
   cargo test --workspace --all-targets --locked
   cargo +1.88.0 check --workspace --all-targets --locked
   RUSTFLAGS='--cfg fuzzing' cargo +1.88.0 check --package dux-core --all-targets --locked
   cargo audit --deny warnings
   cargo audit --file fuzz/Cargo.lock --deny warnings
   cargo deny --locked check
   cargo deny --manifest-path fuzz/Cargo.toml --locked check --config fuzz/deny.toml
   cargo package --workspace --locked
   bash -n dux-macos/scripts/*.sh scripts/*.sh
   bash scripts/check_macos_deployment_target.sh <each macOS release Mach-O>
   ```
3. **Consider cross-platform issues**: Code inside `#[cfg(target_os = "macos")]` won't be compiled on Linux CI - ensure no unused variables leak out
4. **Commit and tag**: `git tag vX.Y.Z && git push origin main --tags`

The tag workflow is strictly ordered: validation/security, four-target builds, crates.io, draft GitHub release plus `SHA256SUMS`, then Homebrew. All actions must remain pinned to full commit SHAs. `HOMEBREW_TAP_TOKEN` must be a fine-grained PAT scoped only to `mjukis-ab/homebrew-tap` with Contents read/write; it is passed only to inline Git in the final job.

## Architecture

- **dux-core**: Core library with tree data structures, scanner, and cache
- **dux-cli**: TUI application using ratatui
- **dux-ffi**: Minimal UniFFI boundary; keep exports coarse, owned, versioned, and free of presentation or cleanup policy
- `dux-core::projection` owns `ArtifactKind`, evidence-gated artifact classification, large-file projection, and clock-injected staleness evaluation. Marker IDs and paths are snapshot evidence, never cleanup authorization; mutation callers must revalidate them. Keep CLI dirty-state coordination, threshold cycling, and display labels out of core.
- `dux-core::domain` owns product-neutral rule/candidate policy. A `RuleRef` always carries stable ID plus nonzero revision; validated rules own category/safety/action/schedule policy, candidates copy those fields, and typed evidence/blockers remain scan facts only. Production candidate construction is crate-private and accepts only the completed fresh-scan witness; the current catalog is selected-root, Informational/RevealOnly, unschedulable, and always blocked by unresolved protected-path authority. Never interpret a persisted candidate, `has_cleanup_operation`, `has_no_known_blockers`, or a rule scheduling flag as planner/executor authority. Keep localized copy in clients via stable text keys and keep schema DTOs, path validation, plans, persistence, FFI DTOs, AI, and execution in their dedicated layers.
- `dux-core::persistence` owns checksummed SQLite schema versions and non-authoritative history. Schema v2 preserves migrated v1 candidate/cleanup rows only as incomplete legacy summaries and stores new ordered paths/evidence/blockers, frozen cleanup effects, and recovery generations separately. Schema v4 binds one strict evaluation lifecycle to the exact succeeded scan snapshot, evaluator/catalog/context identity, normalized time, and complete candidate batch or typed failure; normal engine publication commits that graph in one transaction, while historical scans receive no fabricated rows. The typed candidate/evaluation readers return distinct observation records rather than domain authority, validate bounded children, status/count/time/snapshot/policy/evidence invariants, and reject legacy pollution or post-evaluation standalone inserts. The typed cleanup boundary records complete `planned` observations after exact candidate-fact matching; its separate sealed journal lease retains the cleanup lock, is non-shareable, internally generates an owner, and exact-CASes typed owner/generation transitions. Full bounded journal loads validate the frozen plan plus every dynamic child, derived result, generation, timestamp, and effect-provenance shape. Same-scope recovery writes only for `DefinitelyGone`; `Alive`, `Unknown`, changed boot scope, and Windows death are not recovery authority. Durable effect-start receipts are ordering evidence only, reject cancellation at final revalidation, and this layer performs no effect. Never deserialize a stored candidate/plan into cleanup authority, infer interruption or an effect result from process death, expose raw SQL/owners through FFI/CLI/AI, or let heartbeat age authorize recovery.
- Cleanup-plan records are immutable review data, not approval or executor witnesses. They freeze candidate/rule/scan facts for 15 minutes, derive mandatory estimate/mode warnings, and distinguish Trash, permanent removal, and cloud eviction. Their constructor remains private inside `dux-core::domain::cleanup_plan` until canonical path validation can supply planner-owned target witnesses. Do not expose plan construction to FFI, CLI, Swift, AI, or arbitrary paths; do not add `can_execute`, approval, mode-mutation, or filesystem behavior to these domain records.
- `dux-core::path_validation` is a staged, crate-internal evidence service, not an authorization API. It validates raw host-native syntax before `Path` normalization, binds cleanup targets to one strict scan-root descendant, and captures live no-follow canonical/identity evidence twice. Its snapshots can become stale immediately and must later pass protected-root policy plus executor-time revalidation. Windows inspection currently reopens cumulative full paths rather than resolving relative to retained handles, so it must not become actionable until the executor has handle-bound or equivalent revalidation. Never accept cache-rebuilt `DiskTree` paths as cleanup identity: cached names are currently reconstructed from lossy strings, and the later planner must enforce fresh/lossless scan provenance with a typed source witness before calling this bare-path validator. Keep validator construction out of FFI, clients, AI, cleanup plans, and the legacy CLI until their explicit migration slices.

- A still-live `StagedSnapshot` is narrow current-call rollback authority over only its retained identity, not inventory or scavenging authority. Under an exact current-schema guard, a missing or conflicting temp row must forbid publication, remove only that kernel-locked current-call temp, preserve conflicting metadata, and return corruption. If the current-schema guard cannot be established, close without mutation.
- References to the SQLite root marker as "immutable" above mean its entry and filesystem identity are permanent. Its exact fixed-length legacy-v1 content has one monotonic, writer-locked transition to layout v2 after both cleanup controls are durable; every other rewrite, downgrade, or unknown value fails closed, and older binaries intentionally reject the one-way layout boundary.
- The SQLite final-root inventory above is extended by the exact permanent `<database>.cleanup.lock` and `<database>.cleanup.lock.ready` controls. Legacy owned layouts may add them only while holding the writer lock, must durably flush the lock before the ready control, and only then advance the retained root-ownership marker from layout v1 to v2. Layout v2 with either control missing or malformed fails closed and never recreates it. Retain and revalidate both identities; on Windows open them without delete sharing. The non-expiring cleanup OS lock is distinct from the writer lock and proves exclusion only—never plan, owner, liveness, recovery, journal, target, or effect authority. Future effect paths must order engine cleanup mutex → cleanup lock → connection mutex → writer lock → transaction and revalidate the held cleanup control immediately before every effect.
- `dux-core::persistence::process_liveness` is a crate-private evidence prerequisite, not recovery authority. Its versioned owner token fits the 128-byte schema field and binds PID/start time to a random claim nonce plus a reliable hashed macOS boot session or Linux boot/PID namespace. Only same-scope absence or start-token change is `DefinitelyGone`; foreign scope and every ambiguity are `Unknown`. Because boot and host scope are currently combined, reboot is also `Unknown` until separate stable local-host provenance exists. Windows currently proves exact live matches only and must gain a reliable host/boot scope before reporting death. Never use PID, heartbeat age, lock age, the nonce, changed scope, or `Unknown` to recover, and never expose raw owner identities through FFI/CLI/Swift/AI. The journal lease probes only after dropping database locks, retains/revalidates the cleanup lock, and then exact-CASes the stale phase/owner/generation/heartbeat/cancellation tuple; this liveness module itself performs no journal write.
- `DuxEngine` is one application-scoped opaque session. Calls and close operations are serialized by `EngineService`; close is explicit and idempotent, generated errors are mapped before render state, and ARC release is not a substitute for cancellation or shutdown semantics. `live_engine_instance_count` exists only for linked binding-lifetime diagnostics.
- The macOS scene order is an invariant: keep the window-style `MenuBarExtra` first, followed by the singleton `Window(id: "explorer")` and `Settings`. On the macOS 14 deployment target, the first-scene rule keeps Explorer closed on a fresh launch. Open/focus windows only through `AppActivation`, which uses `NSApplication.activate()` rather than the API deprecated in macOS 14. Keep `LSUIElement` enabled and user-facing shell strings in `Localizable.xcstrings`.
- Build the universal macOS Rust artifact with `./dux-macos/scripts/build-rust-xcframework.sh`; generated output belongs under ignored `dux-macos/Generated/`.
- Regenerate matching Swift bindings and the header-bearing XCFramework with `CONFIGURATION=Debug ./dux-macos/scripts/generate-bindings.sh` or `CONFIGURATION=Release ./dux-macos/scripts/generate-bindings.sh` before building that same Xcode configuration from a clean checkout.
- Synchronous UniFFI calls belong in `EngineService`'s dedicated queue. Convert generated records to Sendable app DTOs before resuming Swift concurrency, and publish render state through the `@MainActor` `AppModel`.
- `VolumeMonitor` samples raw startup-volume capacity through Foundation on a dedicated utility queue. Prefer important-usage capacity for the headline value, retain ordinary available capacity for usage accounting, make fallback provenance explicit, and never infer free space from scan totals. Disk-pressure labels and hysteresis belong in the Rust evaluator, not Swift UI code.
- The macOS app and shared-engine target architecture is defined by the accepted ADRs in `docs/adr/`; keep `ROADMAP.md` and those decisions aligned.
- Run the scanner diagnostics example with `cargo run -p dux-core --example debug_scan -- /path/to/scan`.

## Cache System

- Cache stored in `~/.cache/dux/` (or platform equivalent via `dirs` crate)
- Format: Magic + Version + Metadata + Tree (postcard) + CRC32
- `TreeNode.path` and `is_expanded` are `#[serde(skip)]` - reconstructed on load via `rebuild_paths()`
- `TreeNode.mtime` is captured for files and directories from the same metadata used for size, serialized since cache v6, and remains snapshot evidence rather than mutation authority. Cache v7 invalidates older per-path hard-link totals after deterministic physical-allocation deduplication. Followed links retain `path_is_symlink` while using target metadata; pre-Unix-epoch values unsupported by Serde remain `None`.
- Bump `CACHE_VERSION` in `dux-core/src/cache/metadata.rs` when format changes
- Cache age always means the tree's original scan time; deletion-only cache updates must preserve it.
- `r` starts a cache-bypassing rescan. Keep the previous tree and dirty state until the replacement scan succeeds so failure or quit cannot lose the last usable snapshot.
- Writers use exclusively created `.<cache>.<pid>.<counter>.tmp` files and atomic rename. Join older in-process writers before publishing a newer snapshot; cross-process writes are still last-writer-wins.

## Tree Structure

- Arena-allocated with `Vec<Option<TreeNode>>` - `None` = tombstone (deleted)
- `remove_node()` tombstones node + descendants and propagates size changes up to root
- Footer selection bytes and multi-delete planning use the same effective selection: selected descendants are omitted when an ancestor is selected. The displayed selection count remains the raw number of highlighted rows.

## Deletion

- Permanent filesystem removal is contained in the temporary core-owned `dux-core::cleanup::legacy_cli` adapter. CLI state prepares an opaque target-bound plan before confirmation and consumes it on execution; no UI module, FFI export, or macOS source may call or re-export the adapter. Its public Rust surface is temporary and unsupported, and it does not satisfy the future cleanup-plan/approval/executor authority graph.
- Deletion runs in a background thread to keep UI responsive
- Tree and cache state are updated only after filesystem deletion succeeds
- Failed deletions remain visible and surface an error in the UI
- Delete confirmation captures the entry's filesystem identity without following symlinks. It also captures every ancestor directory identity from the scan root to the target parent; the worker re-checks ancestors and the target before removal and skips changed, missing, symlinked, or reparse-point paths.
- Legacy delete admission validates the complete target—not only its parent—as an absolute, valid-text, control-free strict descendant composed entirely of normal components. It rejects scan-root equality, terminal/intermediate `.` or `..`, outside-root paths, and any target, ancestor, or marker on a different filesystem from the scan root. Preserve these checks when replacing the temporary adapter with the production executor; cached tree names are untrusted input.
- CLI deletion surfaces must say that removal is permanent and must describe deleted-byte totals as scan estimates, never measured freed capacity.
- Build-artifact deletes additionally capture the exact marker-file identities used for classification and re-check them at execution time.
- Confirmed multi-delete batches use at most four named workers fed by a shared queue. All handles remain tracked; graceful quit and `Drop` wait for active and queued items, and an individual task panic is reported as that item's failure without stopping the pool.
- User can continue browsing while deletion happens in background
- Deletion workers are tracked; graceful quit waits for them, applies their results to the tree, then persists the cache. External force termination can still interrupt a filesystem operation.

## Build Artifact Classification

- Classification is fail-closed and tree-aware; directory names alone are not evidence.
- Markers must be exact-case, direct sibling/child regular files and must not be symlinks.
- Current rules: Cargo `target` + sibling `Cargo.toml`; Node `node_modules` + sibling `package.json`; Gradle `build`/`.gradle` + a sibling Gradle build/settings script; Python `__pycache__` + sibling `.py`, `.tox` + sibling `tox.ini`, and `.venv`/`venv` + child `pyvenv.cfg`; CocoaPods `Pods` + sibling `Podfile` + child `Manifest.lock`; Next/Nuxt output + sibling `package.json` + matching framework config.
- `DerivedData`, `Build`, `dist`, `vendor`, and `.cache` are intentionally not classified yet.
- “Marker-matched” means likely tooling ownership, not guaranteed reproducibility. Permanent deletion remains manually confirmed.
